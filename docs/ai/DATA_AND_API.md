**Lesson video** (Issue #447). `GET /me/lessons/{id}` sends `video: {"embed_url": …}` or `null` (backend `app/services/learning/student.py`, from the lesson's `classroom_embed_url`, which the Admin Panel sets). Source-documented, not seen live: whether production carries any URL is `UNKNOWN`.
- **Read:** `embed_url` into `CourseExercise.videoUrl`, exactly as sent, when it is a string that parses as an `http`/`https` URI with a host — the rule the backend applies when it stores it (`fields.http_url`). A fragment (`#t=30`) is allowed.
- **Failures unchanged:** a missing `video` key, or a `video` that is neither an object nor `null`, is a `server` failure.
- **No playable video:** `video: null`, or an `embed_url` that is missing, not a string, or not such a URL. The lesson still loads, and the header draws the existing no-video state (`PRODUCT DECISION` D1).
- **Play** hands the URL to `openExternalUrl` (external application, no new dependency; `PRODUCT DECISION` D2). The provider (YouTube, Drive, Classroom, …) is never assumed. A refused launch shows `CourseLearningStrings.unexpectedError` as a SnackBar. Opening the video does not complete the lesson (Issue #209).

**Teacher Home** (Issue #229). `teacher_id` is the teacher's `GET /auth/me` `actor_id` (verified live with the teacher test account: the schedule answers for it, assignments' `teacher_id` and the public `cohort.teacher.id` carry it). The schedule answers `{teacher_id, cohorts: [...]}`, each cohort in exactly `GET /cohorts`'s shape, parsed by the same `cohortFromJson`. Fields read: `name`, `course.id`/`title_*`, `classroom.name` (nullable — omitted when null), `enrolled_count`, `start_time`, `end_time`, `start_date`, `end_date`, `meeting_days`. Each class's track badge is the public `GET /courses` `level` (`adult`/`junior`) matched on `course.id`, best-effort: no badge when the catalog cannot be read, or when the course has no `level` (Issue #485). A teacher token gets `403` from `GET /me/cohorts`, so no student endpoint is called for a teacher. The repository refuses an `actor_type` other than `teacher` before sending.

**Teacher Schedule** (Issue #231). Both teacher endpoints were verified in backend reconnaissance (task-supplied contract; no captured response is in the repository). `GET /teacher/cohorts/{cohort_id}/sessions` takes optional `from`/`to` (`YYYY-MM-DD`) and answers `{cohort_id, sessions: [{id, cohort_id, session_date, start_time, end_time, topic_id, created_at}]}`; read: `id`, `cohort_id`, `session_date`, `start_time`, `end_time` (wall-clock, read as local time like a cohort's times). Whether `to` is inclusive is `UNKNOWN`, so the app asks one day past the week and keeps only the week's days. It is asked once per class whose `start_date`…`end_date` reaches into the week on screen — one request per running class, never one per session; calendar blocks come only from these sessions, never from `meeting_days`. `GET /teacher/sessions/{session_id}/attendance` answers `{session, counts: {present, late, absent, excused}, students: [{student_id, name, status, method, checked_in_at}]}`; only `counts` is read. Unmarked students are returned as `absent` with `method: null` — there is no "not marked" status. The held-session summary shows `present + late` of the four counts' sum (the session's roster); `absent` and `excused` are not attended. It is read only for the session the teacher taps. A block is "held" (the reference's light block) once the session's end time has passed — a clock rule, `PRODUCT DECISION`: no endpoint reports that a session was "entered". Nothing in Teacher Schedule writes.

**A session's `end_time` may be null** (Issue #479; verified from the backend: `ClassSession.end_time` is nullable, `_apply` makes it optional while `start_time` is required, and `generate_sessions` copies the cohort's nullable `end_time`; `session_dict` and `session_brief` send it as-is). The app keeps such a session: its label is the start alone (`18:30`), it counts as over only once its day is over, and the grid draws it at the minimum block height — no end time is shown or made up. `start_time`, and an `end_time` that is present but unreadable, are still a `server` failure.

**Schedule change — phase 1** (Issue #449; "Цаг солих" → "Багш нар"). **Documented contract, deployment unverified:** `ai-academy-backend` `docs/schedule_change_api_v1.md` at `c6e6ce0` (2026-10-13), covered by its `tests/test_schedule_change_*.py`. No live response is captured, and whether the deployed backend serves these routes is `UNKNOWN`. Both calls go through `HttpScheduleChangeRepository` and `teacherSend`, so a refusal keeps its `{"error": code}`.
- `GET /teacher/sessions/{session_id}/eligible-teachers` → `{session_id, items: [{id, name, photo_url}]}`: the active teachers not teaching at that time, in the server's order. Read: `session_id` (must be the session asked for), `id`, `name` (a string; a teacher whose name is blank is left out of the list rather than offered unnamed — Issue #537, product decision). `photo_url` is always `null` per the contract, so rows keep the placeholder avatar (a string is accepted; any other value is a `server` failure). Refusals: `404 session_not_found`, `409 session_started`.
- `POST /teacher/schedule-change-requests` with exactly `{"session_id", "recipient_teacher_id", "message": null}`: the screen has no message field. Only `201` (created) or `200` (an identical retry) whose request object names the same `session_id`, `recipient.id` and `status: "pending"` is a confirmed send; anything else is a failure, never a success. Refusals: `409 recipient_busy`, `request_pending`, `session_already_covered`, `session_started`; `404 session_not_found`, `recipient_not_found`.
- **Screen:** "Багш нар" (`TeacherScheduleChangeScreen`) lists the teachers, or says none is free (`requestsEmpty`). A send shows "Хүсэлт илгээгдлээ" only after confirmation, then that row reads "Хүлээгдэж байна" for as long as the screen is open; while a send is in flight every pill is inert. A failure is a SnackBar. Each documented code has its own line (`TeacherScheduleStrings.requestFailure`, the app's own copy, `PRODUCT DECISION`).
- **A backend without these routes:** a refusal carrying no documented code (Flask's own 404 page has none) reads as the unavailable line (`requestsUnavailable`), never as an empty list or a sent request.
- **Phase 2 — answering a request** (Issue #453; same contract, deployment unverified). A teacher answers from the notification: a `schedule_change_request` whose `data` has positive integer `request_id` and `session_id` opens `TeacherIncomingRequestSheet` (`showIncomingScheduleChangeRequest`) instead of the detail; a malformed one, and every other `kind`, opens the detail as before.
  - `GET /teacher/schedule-change-requests/{id}` first — the request object (contract §3), read strictly: `id` (must be the one asked for), `session_id`, `status` (`pending` / `accepted` / `rejected` / `cancelled` / `expired`), `sender.name` (a string; a blank one reads as empty, so the sheet still opens and an accept or reject the server made is not reported failed — Issue #537), and the `session` brief (`date` required; `start_time`, `end_time`, `title`, `cohort_name`, `room` each a string or null). The server settles expiry on read. The sheet's card is drawn from that brief — no student count or track badge, which the request does not carry.
  - "Татгалзах" / "Зөвшөөрөх" show only while the read says `pending`, so a stale notification shows where the request stands (a status line) and no actions.
  - `POST …/{id}/accept` with `{}` and `POST …/{id}/reject` with `{"reason": null}` (no reason field). Only a `200` whose request object is that request at `accepted` / `rejected` is a decision; anything else is a failure, never a resolved sheet. Taps while one is in flight are ignored.
  - Refusals: `request_already_resolved` and `session_started` re-read the request (its status line then shows; a failed re-read closes the actions); `schedule_conflict` and `session_already_covered` turn accept off and keep reject; `403 not_recipient` and `404 request_not_found` close the actions; network, session and server failures keep them for a retry. A request that cannot be read shows why, with no actions; a no-code refusal is the unavailable line.
  - The status and error lines are the app's own (`TeacherScheduleStrings`, `PRODUCT DECISION`), in the selected language since Issue #547.
- **Phase 3 — covered sessions in Teacher Schedule** (Issue #455; same contract §6, deployment unverified). Each displayed week also reads `GET /teacher/sessions?from=<week's first day>&to=<its last day>` (`YYYY-MM-DD`; both bounds always sent, the range includes both days) through `HttpTeacherScheduleRepository.getAssignedSessions`, alongside the unchanged per-cohort reads. Its `items` are read strictly (`assignedSessionsFromJson`):
  - `assignment_type: regular` — one of the teacher's own sessions: only `id` and `covered_by` (an `{id, name, photo_url}`, or null; a blank `name` keeps the session covered, only unnamed — "Орлон заагдсан" with no name — Issue #537, MOB-07) are read, and the name is matched onto the cohort read's session by id.
  - `assignment_type: covering` — a session the teacher covers: `date`, `start_time`, `end_time` (all required: it is placed from them, and no time is invented), `request_id` (integer), the brief's `title` / `cohort_name` / `room` (string or null) and `original_teacher.name` (or null; a blank name reads as none, Issue #537). Any other `assignment_type`, or a malformed item, is a `server` failure.
  - A covering session joins the week in date-and-time order (ties by id), only within the week, and never twice (a session id already drawn is skipped). It has no `TeacherClass` (`ScheduledSession.covering`): its card is the brief, with no student count or track.
  - Labels (`TeacherScheduleStrings`): a covering session reads **"Орлон заах"**, an own session another teacher covers **"Орлон заагдсан · {name}"** ("Covering" / "Covered · {name}" in English, Issue #547) — on the grid block's first line, as a capsule over the day-list card, and over the sheet's card. Ordinary sessions are drawn exactly as before.
  - Actions: a covering session's sheet offers nothing — no "Цаг солих", "Ирц бүртгэх", manual marking, QR, or attendance summary (the covering teacher has no attendance access in v1). A covered own session keeps its attendance actions but not "Цаг солих" (the backend answers `409 session_already_covered`).
  - If this read fails, the week fails with the existing error and Retry — never a week missing its covers.
- **Not done:** a received-requests list, `schedule_change_response` handling for the sender, cancel, and a reject reason. "Багш нар" still does not restore a row's pending state on reopening; a second send for the same session answers `409 request_pending`, which the screen says.

**Teacher attendance registration** (Issue #374). Verified from the backend's source (`app/routes/attendance.py`, `app/services/attendance/checkin.py` on `ai-academy-backend` `main`) and `docs/mobile_api_v1.md` §8; no live response is captured, and no test calls production. Caller: a teacher, or staff with `cohort:manage` (else `403 forbidden`); a session the caller does not teach is `404 session_not_found`. Errors are `{"error": code}`; teacher writes go through `teacherSend`, which keeps the code as `TeacherFailure.code` (reads do not parse it).
- `POST /teacher/sessions/{session_id}/qr` — no body; answers `{token, expires_at}`. The token lives 5 minutes (`QR_TTL_MINUTES`) and **each issue voids the previous one**; off the session's Ulaanbaatar date it is `409 session_not_today`. The QR screen re-issues every 4 minutes and times expiry from the token's arrival (5 minutes), not from `expires_at`, so a phone with a wrong clock never shows a dead code as live.
- `GET /teacher/sessions/{session_id}/attendance` — the roster (`students[]`: `student_id`, `name`, `status`, `method`, `checked_in_at`; active enrolments only, by name; unmarked = `absent` with `method: null`) and `counts`. Polled every 15 s on the QR screen; read once by the manual screen. A `status` outside `present`/`late`/`absent`/`excused` is a `server` failure — never mapped onto one of the four.
- `PUT /teacher/sessions/{session_id}/attendance/{student_id}` with `{"status"}` — creates or overwrites, always setting `method: "manual"`; answers `{student_id, session_id, status, method, checked_in_at}`; `400 invalid_status`, `404 student_not_found`. No batch endpoint: confirming sends **one PUT per changed row**, in sequence; an unchanged row (a QR check-in, a `late`, an `excused`) is never sent. A stored row is never resent; a failed one is the only thing a retry sends.
- "Ирц бүртгэх" is live only on the session's date in Ulaanbaatar (`attendanceOpenOn`: UTC+8, no daylight saving — the backend's `Asia/Ulaanbaatar` "today"), on the upcoming sheet, where it opens the QR screen. A session whose end time has passed opens the held sheet: on its Ulaanbaatar date that sheet keeps the summary and adds "Гар аргаар бүртгэх", straight to the manual screen (Issue #376) — the PUT takes a mark at any time — and the summary re-reads on return; on any other date the held sheet has no attendance action. QR is offered only from the upcoming sheet.
- **The QR payload — confirmed (Issue #380): the raw `token`.** The code encodes the issued `token` string itself, with no URL or JSON around it — what the student's `POST /me/attendance/check-in` sends back as `{"token"}` (the backend strips whitespace and looks it up by hash; its own tests send the issued token verbatim). The token is a live credential: it is kept out of logs, error messages, widget keys (the code is keyed by a token count) and semantics (read out as "Ирцийн QR код"), and `AttendanceQrToken.toString` redacts it. No code is shown until a token has arrived. Students cannot scan it from this app yet: the student scanner is UI only (no camera, no check-in call — Issue #202). Also unconfirmed: any backend constraint on partial writes (ordering, rate limits) — the UI keeps stored rows and retries only failed ones. **Server changes before saving (Issue #378):** immediately before writing, the manual screen reads `GET …/attendance` again and sends a changed row only if the server still holds the `status` and `method` the teacher's edit was based on. Otherwise the row is held as a conflict, showing the server's record and the teacher's choice, until the teacher keeps the server value (nothing sent) or applies their own (sent on the next confirm, after another re-read). A failed re-read sends nothing. A write that already landed (server `manual` with the teacher's status) is not resent. Untouched rows take the server's latest. **Remaining race:** the PUT is an unconditional overwrite and the backend has no conditional write (no version, ETag or expected status), so a change landing between the final re-read and a row's PUT — seconds, one PUT at a time — can still be overwritten; closing it needs a backend change. QR check-in itself never overwrites an existing record (`check_in` returns the first record), so the risk runs only from a manual edit onto the server. Back navigation is held while a confirm's writes are in flight, so a save is never cut short.

**Teacher Programs — formerly the Gradebook** (Issues #233, #390). A missing English title is not a failure; a body without the `assignments` list, a `title` that is not an object, or a title side that is not a string is a `server` failure. **Assignments stay one simple list, not grouped by module** (`PRODUCT DECISION`, Issue #394), so the Figma's "Modules N" is drawn as "Даалгавар N", the assignment's place in the list.

### 1.1 Fields read by the Home dashboards

Adult Home (`EnrolledHomeDashboardRepository`) and Junior "Сурлагын явц" (`ApiJuniorProgressRepository`, which maps that same dashboard) read only these fields. Each shape is the verified production response recorded on the repository; `mobile_api_v1_1.md` is the contract they were checked against.

**Which cohort the dashboard is about** (Issue #495), for a student enrolled in more than one. Adult Home, Junior Home and Junior Progress all take the dashboard's choice. It is made from the enrolled cohorts' `start_date` / `end_date` against today's **Ulaanbaatar** date (`ulaanbaatarToday`), never from `status`: the backend sends only `draft`, `open` and `closed`, which say nothing about whether a cohort is under way. In order:

1. **In progress:** start ≤ today ≤ end, both ends inclusive. A missing or unparseable date leaves that end open (as `LessonSchedule` treats it); a cohort with neither date is not in progress on its dates alone. If several qualify, the first in `/cohorts` order wins.
2. **Upcoming:** start after today; the earliest start wins.
3. **Ended:** end before today; the latest end wins.
4. Otherwise, the first enrolled cohort in `/cohorts` order.

Ties keep `/cohorts` order.

| Endpoint | Fields read | Used for |
|---|---|---|
| `GET /me/cohorts` | entry `cohort_id`, `progress_pct` | which cohorts the student is in; progress fallback |
| `GET /cohorts` (still lists ended cohorts: 8 listed, 3 past `end_date`, statuses `closed`/`open`, verified live 2026-10-08 for the Certificate screen, PR #245; whether an archived cohort drops out is `UNKNOWN`) | `id`, `name`, `status`, `course.slug`/`title_*`, `start_date`, `end_date`, `start_time`, `end_time`, `meeting_days` | the cohort in view; `LessonSchedule` → next lesson, the attendance calendars' lesson days, and (`start_date` / `end_date`) the first and last month they page to (Issues #200, #457) |

### 1.2 Push notifications (Issue #398)

**On only with Firebase configured.** `main` starts Firebase (`startFirebasePush`) and attaches `PushNotifications.instance`; without the project's configuration it returns null and push is off — every push method is then a no-op and the app behaves as before. Android reads `android/app/google-services.json` natively (the Google Services Gradle plugin 4.5.0 is applied **only when the file exists**): the default Firebase app must exist when a push starts the process, and `firebase_core` does not persist options given in Dart. iOS takes its options as `--dart-define`s (`FIREBASE_IOS_API_KEY`, `FIREBASE_IOS_APP_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_PROJECT_ID` — the `GoogleService-Info.plist` values for `com.aiacademyasia.aiaMobile`), so no plist is added to the protected Xcode project. **No configuration is in the repository**: none was available, and none is invented.

**Where the files go, none committed (Issue #421).** `.gitignore` covers each of them before anyone has one:
- **Android:** `android/app/google-services.json`. Whether to commit it eventually is a `PRODUCT DECISION` for the Firebase project's owner; Firebase treats it as an identifier, not a secret.
- **iOS:** copy `firebase_ios.example.json` (committed, with empty values) to `firebase_ios.local.json` (ignored) at the repository root, fill in the four values, and build with `--dart-define-from-file=firebase_ios.local.json`.
- **`ios/Runner/GoogleService-Info.plist`:** ignored too. The app doesn't read it.
- **Never in this repository:** the Firebase service-account key (`*firebase-adminsdk*.json`, `*service-account*.json`) is the backend's `FCM_CREDENTIALS`, and the APNs key (`*.p8`) is uploaded to the Firebase project.

**Token lifecycle** (`lib/features/notifications/push/push_notifications.dart`). Nothing happens on Splash or Login. On the first signed-in home route (`HomeRoutes.adult` / `junior` / `teacher`, seen by `PushNotifications.routeObserver`): the permission is checked and asked when undecided — on iOS whenever the OS reports `notDetermined` (a reinstall resets it, while the secure-storage memory, in the Keychain, survives), on Android 13+ **at most once per install** (it reports "not asked" and "refused" alike, so `SecurePushPermissionMemory` remembers asking); with it granted the FCM token is registered with `POST /me/push-tokens` and the session's own bearer token. Refused: nothing is registered; in-app notifications are unaffected. A token is registered once per session generation, and a start joins only a start of the same generation (a start still running for a signed-out account never swallows the next account's); a refreshed token (`onTokenRefresh`) is registered for the signed-in generation only; a registration still in flight when its session ends is not recorded. A failed registration is retried on resume, the next refresh or the next home route — never in a loop. **Sign-out** (`signOutToLogin`) first removes the token from the account (`DELETE /me/push-tokens`, 5 s) while the session can still authenticate it, then deletes it on the device (`deleteToken`), so the next account here gets a new token and a removal that failed still delivers nothing. A session that ended without sign-out (renewal failed) only deletes it on the device. `firebase_messaging` 16.7 offers registration tokens (`getToken`), not FIDs; FCM v1's `Message.token` still accepts them.

**The Profile Notification switch (Issue #429).** `NotificationPermissionSwitch` shows `PushNotifications.permissionState`, the OS permission read without prompting.
- **When it is read:** when Profile opens (`refreshPermission`), on every resume, and by each start.
- **Values:** on when granted **and** the "Мэдэгдэл" channel (`aia_default`) is not blocked; off when denied, not determined, or the channel is blocked (Issue #433).
- **Why the channel matters:** `firebase_messaging` reports only the app-level permission (`POST_NOTIFICATIONS` on API 33+, `areNotificationsEnabled()` below), yet Firebase posts every push into that channel. Blocked, pushes arrive and are never shown. `MainActivity`'s `isDefaultChannelBlocked` reads the channel's importance (`NONE` = blocked) and never changes it. It answers false below API 26, for a missing channel, and when the read fails.
- **A tap** opens this app's notification settings (`openNotificationSettings`). On Android that is `MainActivity`'s `com.aiacademyasia.aia_mobile/notification_settings` channel: `ACTION_APP_NOTIFICATION_SETTINGS` on API 26+, the app-details screen below that. On iOS it is `app-settings:` through `url_launcher`, so the protected `AppDelegate.swift` is untouched. The switch never changes the permission itself, and a failure to open answers false without throwing.
- **Coming back allowed:** the existing resume path registers the token, with no prompt. This is the only way back on Android 13+, where the app asks once per install.
- **With push off,** the switch is inert and off.
- **Not seen on a device yet:** the phone was returned.

**Payload** (from ai-academy-backend#2, not yet on its `main`): `notification {title, body}`; `data` — `kind`, the recipient's own `notification_id`, and the in-app notification's own `data` keys, every value a string. **Foreground**: the OS shows nothing, so the bell refreshes and a SnackBar shows the title with "Харах". **Tap** (SnackBar, background, or a terminated launch — the launch tap waits for the home route so Splash cannot replace it): `NotificationScreen`, and over it `NotificationDetailScreen` for `notification_id` when it is in the loaded list, marked read as a tile tap does. No `kind` deep-links further — the in-app list does not either (`PRODUCT DECISION`, kept). No background handler: notification messages are displayed by the OS.

## 3. Transport layer

Two entry points, split by failure family — not by accident:

- **`lib/core/api/api_client.dart`** — `getJson` (throws `ApiFailure` on any non-2xx), `getRaw` and `postWithoutBody` (return **every** status so an authenticated caller can read 401 as "sign in again"). All three turn a request that never completed into `ApiFailureKind.network`.
- **`lib/features/auth/data/auth_http.dart`** — `postJson`, which encodes a JSON body and reports `AuthFailure`.

`getJson`'s shared status mapping has no 401 case on purpose: it serves endpoints confirmed to need no auth, so a 401 there would be the API misbehaving, and giving it a "session expired" reading would force that case onto every public caller's `switch`.

### 3.1 API base URL and a local backend (debug only, Issue #388)

**One configuration.** `ApiConfig` (`lib/core/api/api_config.dart`) holds the API origin. All 16 HTTP repositories default to `ApiConfig.baseUrl`; a test may still inject its own `baseUrl`. That includes sign-in and session refresh (`HttpAuthRepository`, which `SessionRefresher` uses), the teacher endpoints, and attendance check-in. No other file in `lib/` names the production URL, and `test/core/api/api_config_test.dart` enforces both rules.

**Production unless a debug build says otherwise.** `--dart-define=AIA_API_BASE_URL=<origin>` is honoured **only when `kDebugMode`**. Release and profile builds ignore it and always use `https://api.ai-academy.asia`. An empty value, or the production URL itself, means production. The value must be a bare `http(s)://host[:port]` origin, with no credentials, path, query or fragment. **Anything else stops the app at startup** (`InvalidApiBaseUrl`, from `main`), rather than falling back to production; the message names the broken rule, never the value. While an override is active, every screen shows a red **"API: host:port"** pill at the top (`ApiOverrideBanner`), and the debug console logs `AIA API override: host:port`.

**Running against a local backend.** These steps start and seed a *local* server; nothing here touches production. The backend is `ai-academy-asia/ai-academy-backend`; see its `README.md`.
1. **Backend on the Mac:**
   - Python virtualenv and `pip install -r requirements.txt`.
   - `cp .env.example .env`, local values only.
   - `docker compose --profile dev up -d` (the README notes Postgres on host port 5433).
   - `flask db upgrade` (the migrations exist; skip the README's `flask db init` / `migrate`).
   - Test data with `flask seed programme <key>`: `@test.ai-academy.asia` accounts and class sessions on the programme's weekdays. If today is not a class day, create today's session locally through the teacher endpoint.
   - Run `python wsgi.py`; it listens on `0.0.0.0:8000`. Its "today" is Ulaanbaatar's.
2. **iOS simulator:** `flutter run --dart-define=AIA_API_BASE_URL=http://localhost:8000`. The simulator shares the Mac's network, and has no camera, so the student scanner shows its "unsupported" state there.
3. **Physical iPhone** (needed for the camera): put the Mac and the iPhone on the same Wi-Fi.
   - Find the Mac's LAN address (`ipconfig getifaddr en0`).
   - Run `flutter run --dart-define=AIA_API_BASE_URL=http://<mac-lan-ip>:8000`.
   - Allow Python through the macOS firewall when asked.
   - Allow **Local Network** access when iOS asks: iOS 14+ asks before an app reaches a LAN address.
4. **An end-to-end QR check:**
   - Sign the teacher in on the simulator and open today's session → "Ирц бүртгэх"; the QR appears.
   - Sign the student in on the iPhone and open the check-in entry (Junior node, or Adult "Ирц бүртгүүлэх" during the lesson), then scan the simulator's screen.
   - The teacher's count updates within 15 seconds.

**Limitations:**
- **Plain HTTP:** the app's HTTP client is `dart:io`, which iOS's App Transport Security and Android's cleartext policy are not expected to block. This is **not yet verified on a device**.
- **Android emulator:** reaches the Mac at `http://10.0.2.2:8000`.
- **Saved sign-ins don't follow the server:** a saved session belongs to the server that issued it, but the session store does not record which. **Sign out before switching** between a local and a production build. Otherwise the saved token is sent to the other server, where it is refused (401, which clears it) or, for a production token, exposed to the local machine.
- **Seeded accounts may also exist in production,** so check the "API: host:port" pill before signing in with one.

## 4. Failure taxonomy

Eight failure types, each scoped to a domain so no caller has to `switch` over cases that cannot occur in its context.

| Type | Kinds |
|---|---|
| `ApiFailure` (`core/api`) | `network`, `server`, `notFound`, `unexpected` |
| `AuthFailure` (`auth`) | `invalidCredentials`, `sessionExpired`, `network`, `server`, `unexpected` |
| `CurrentUserFailure` (`auth`) | `rejected`, `network`, `server`, `unexpected` |
| `EnrollmentFailure` (`enrollments`) | `rejected`, `network`, `server`, `unexpected` |
| `HomeFailure` (`home`) | `network`, `server`, `unexpected` |
| `AttendanceFailure` (`attendance`) | `sessionExpired`, `rejected`, `network`, `server`, `unexpected` |
| `LedgerFailure` (`payments`) | `sessionExpired`, `rejected`, `network`, `server`, `unexpected` |
| `CourseLearningFailure` (`course_learning`) | `sessionExpired`, `notEnrolled`, `notFound`, `locked`, `contentRequired`, `contentTooLong`, `submissionEmpty`, `invalidLink`, `descriptionTooLong`, `pastDue`, `noAttemptsLeft`, `attemptFinished`, `alreadyAnswered`, `unsupportedFileType`, `fileTooLarge`, `network`, `server`, `unexpected` |
| `ContractFailure` (`contracts`) | `sessionExpired`, `network`, `server`, `unexpected`, and from the body's `error` code (§2.2): `forbidden`, `contractNotFound`, `invalidFields` (+ `fieldErrors`), `agreementRequired`, `signatureRequired`, `invalidSignature`, `emptySignature`, `signatureTooLarge`, `alreadySigned`, `contractCancelled`, `templateMissing`, `templateInvalid`, `notSigned`, `storageError` |

`notFound` exists on `ApiFailure`, because a 404 on `GET /courses/{slug}` is a real, distinguishable outcome (stale link, removed course) a screen may want to word differently, and on `CourseLearningFailure`, for the contract's `*_not_found` 404s. `CourseLearningFailure`'s 400/409/413 kinds are read from the body's `error` code, which the contract (§0) says the app branches on.

**Controllers convert these into `String? errorMessage`.** Widgets never catch failures.

## 5. Authentication and session

```
LoginScreen → LoginController → AuthRepository.login()
                                      ↓ AuthSession {accessToken, expiresIn?}
                              AuthSessionStore.instance.save(session)
                                      ↓
   every authenticated repository reads AuthSessionStore.authorizationHeader
                                      → {'Authorization': 'Bearer <token>'}
```

Facts that constrain any auth-adjacent work:

- **Persisted across restarts** (Issue #235). `main` calls `AuthSessionStore.instance.attach(SecureSessionPersistence())` before `runApp`: the stored session (access token, refresh token, absolute access-token expiry, `user_type`, and since Issue #286 `user_id`, as one JSON value under `aia.auth.session` in `flutter_secure_storage`) is restored, and every `save`/`clear` is written through in order — so a rotated refresh token is what the next launch uses, and sign-out or a dead session leaves nothing behind. An unreadable value restores nothing. A store never attached (every test's `AuthSessionStore()`) is in memory only. Nothing listens to app lifecycle events: backgrounding never touches the session.
- **The signed-in account's id** (Issue #286) is `GET /auth/me`'s top-level `id` (`CurrentUser.id`), the user account. It is not `actor_id` (the student or teacher record), not `profile.id`, and not the role or email. The login and refresh responses don't carry it.
  - Every successful `/auth/me` read records it on the session it was asked for (`AuthSessionStore.identify`), guarded by `accountEpoch` so a late answer never identifies a later sign-in.
  - It is persisted with the session as `user_id` and kept across a renewal (`save(…, renewal: true)`).
  - A new sign-in starts unidentified, and `clear()` forgets it. A session saved before #286 has no `user_id` until the next `/auth/me`.
  - The theme preference is kept per account under it.
  - `BACKEND GAP`: no endpoint stores the preference, so it is per device and per account, not synced across devices.
- **Singleton with injection** — `AuthSessionStore.instance` is the app's store; every repository accepts one so tests can pass their own.
- **Sign-out** (`signOutToLogin`, the Adult, Junior and Teacher Profiles' log-out, each behind `confirmSignOut`): `POST /auth/logout` with the login response's `refresh_token` (kept on `AuthSession.refreshToken`, and rotated by every renewal), then `AuthSessionStore.clear()` **whatever the revoke did**, then the stack is replaced with `/login`. A failed revoke is never shown.
- **Refresh and retry** (Issue #176). Every authenticated repository sends through `AuthenticatedClient.instance` (`auth/data/authenticated_client.dart`), which acts only on requests carrying `Authorization`:
  - **before sending**, an access token past its reported `expires_in` is renewed first (`isAccessTokenExpired()`);
  - **on a 401** whose `error` is one of the contract's token codes — `authentication_required`, `token_expired`, `invalid_token`, `account_inactive` — the session is renewed and the request **retried once** (body buffered, so uploads replay too). A second refusal is returned as is: no loop. Any other 401 (`invalid_credentials` from change-password's wrong current password, or no code) passes through untouched.
  - **Renewal** is `SessionRefresher.instance`: `POST /auth/refresh {refresh_token}` → the login response's shape with a **rotated** refresh token (confirmed live; a spent token answers `401 refresh_token_reused`, an unknown one `invalid_refresh_token`). It is **single-flight** — concurrent 401s wait for one refresh, and a request refused on an already-replaced token just retries — because two refreshes with one token would end the session.
  - **When renewal is refused** (a 401/403 from `/auth/refresh`, or no refresh token), the session is cleared — no `/auth/logout`, the token is already dead — and `onSessionEnded` fires once. **When it merely could not complete** (network, timeout, 5xx — `SessionRefresher.transientFailures`), the session is kept and the next request tries again (Issue #235). **A TLS failure during renewal is a network failure too** (Issue #339): both transports map `TlsException` / `HandshakeException` to the network kind, so a captive portal, a wrong device clock or a certificate problem keeps the session rather than signing the student out — the handshake fails before anything is sent, so the refresh token is not exposed. Before #339 such a failure escaped the transport as a raw exception and ended the session; `main` wires it (`returnToLoginWhenSessionEnds`) to replace the whole stack with `/login` through `appNavigatorKey`.
  - `isExpired()` now means the *session* is dead: access token past its lifetime **and** no refresh token to renew it. When the backend sent no `expires_in`, the 401 is the authority.
- **Splash restores a held session with `GET /auth/me`** (Issues #235, #435). No session, or a dead one (`isExpired()`), goes to Login without asking. A `network` failure (no connectivity, DNS, timeout, TLS) keeps the session and Splash: "Интернэт холболтоо шалгаад дахин оролдоно уу." with a Retry that repeats the whole restore — the session check and `GET /auth/me` — one request at a time, then hands off as usual. `sessionExpired`, `rejected`, `server` and `unexpected` go to Login, as before. Nothing is cached: there is no offline Home.
- **`GET /auth/me`** returns `CurrentUser { id, actorId, actorType, email, role, isActive, mustChangePassword, profile }` with `UserProfile { id, firstName, lastName, phone, uiMode }`. `profile.uiMode` is what drives the Home track badge — nothing on a cohort or course reports it.
- **`must_change_password` gates Home** (Issue #182). Right after sign-in, and when Splash restores a held session, `GET /auth/me` is read; when `must_change_password` is true, `openSignedIn` (`auth/presentation/home_route.dart`) replaces the route with the existing "Нууц үгээ тохируулах" screen (`ResetPasswordScreen`, `POST /auth/change-password`) instead of Home. It is required: there is no skip, and nothing is underneath to pop back to. Home opens once the change succeeds. The flag is read from `/auth/me` because that is where it is confirmed; whether the login response carries it is `UNKNOWN`. When the check itself fails, sign-in continues to Home as before (`PRODUCT DECISION`, #182), and the next sign-in asks again. Whether the change clears the flag server-side is `UNKNOWN`: the app does not re-check.

## 6. Bilingual and unconfirmed-shape handling

- **`LocalizedText {en?, mn?}`** (`core/models`) — the `{"en": …, "mn": …}` wire shape, first seen on `Course.title`/`tagline`. **Which side is shown** (Issue #501): `preferredText` / `LocalizedText.preferred`. With Mongolian selected (the default): Mongolian first, English when Mongolian is empty, as before. With English selected (`ContentLanguage.prefersEnglish`, set by `AppLocaleController`): English when it holds more than whitespace, otherwise that Mongolian-first reading. Text resolved while a response is parsed (most of course learning) follows a language change on the next load; text chosen while drawing (course, cohort and contract cards) follows at once. Note the cohort list endpoint sends **flat `title_en`/`title_mn` instead**; `CohortCourse` builds a `LocalizedText` from those. The two endpoints genuinely differ.
- **`describeJsonLines`** (`core/utils/describe_json.dart`) — for fields whose *name* is confirmed but whose *shape* is not (`curriculum`, `instructors`, `prerequisites`, `whats_included` on course detail). Those stay `Object?` on the model and are rendered generically rather than asserted into a guessed structure. **This is the house pattern for "confirmed name, unconfirmed shape" — reuse it instead of inventing a type.**
- **Nullable fields confirmed by production responses.** The models make a field nullable only once a real response shows it `null`, and the parsers fail loudly on anything else — so such a failure means *loosen the model*, not *the backend is broken*. ## 7. Course Learning integration and the sample boundary

**`lib/features/course_learning/` runs on the real API.** `CourseLearningRepository` declares twelve methods — the learning path, a module's lessons, a lesson's detail, the note save, the lesson completion, a material's download link, the assignment submission, the student file upload, and the four quiz-attempt calls — and `HttpCourseLearningRepository` implements every one against `course_learning_api_contract_v1.md` §2.1–§2.8. Each method documents its endpoint and the shape it reads; the screens default to it. See [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) §2 for the endpoint list and what is deliberately not integrated.

`SampleCourseLearningRepository` still implements the same interface with fixed, hand-authored content that ignores `courseSlug`/`moduleId`/`lessonId` — the note save and the quiz attempt are simulated locally, while its submission, upload and material download throw — but **only tests construct it** (the quiz goldens among them). Consequences to keep in mind:

- Models carry **pre-formatted display strings** — `scheduleLabel` `"08/04 • Да • 09:00"`, `durationLabel` `"24:15"`, `sizeLabel` `"10 MB"`, `timestampLabel` `"Today, 14:20"`. `HttpCourseLearningRepository` builds them on the client from the contract's raw fields (dates, `duration_seconds`, `size_bytes`, timestamps); they are frontend requirements, **not** proposed backend fields.
- **A lesson section's `title` may be null** (Issue #481; verified from the backend's `app/services/learning/fields.py`: `_loc` is nullable for a section's `title` and `body`, the key is always written, and `mn` may be `""`). The app reads it like `body` — `''` then — and the expanded description draws no heading for it; a missing `title` key or a non-object title is still a `server` failure.
- **A section bullet may carry blank text** (Issue #483; same source: each bullet is `_loc(..., nullable=False)` — an object whose `mn` is a string that may be `""`, and whose `en` is a string or `null`). A blank bullet reads as `''` in server order and the expanded description draws no line for it. A `null` or non-object bullet, a text-less bullet whose `mn` is missing or not a string or whose `en` is neither a string nor `null`, and a non-list `bullets` are still `server` failures.
- **A lesson's `duration_seconds` may be null** (Issue #477; verified from the backend: the column is nullable, `create_lesson` sets none, and authoring takes `nullable=True`; `GET /me/modules/{id}/lessons` and `GET /me/lessons/{id}` always send the key). The app's `durationLabel` is then empty and no duration is drawn (Lesson List row, video header, module card); a missing key, a non-number or a negative number is still a `server` failure.
- **`assignment.submission.feedback.mentor` is null for a staff review** (Issue #473; verified from the backend's `app/services/assignments/review.py` and `serializers.py`: a non-teacher reviewer stores no teacher, and `mentor_dict` answers null). The key is always sent. The app keeps the review's message and time and leaves the Mentor Feedback card's author row out — no name or role is invented; a missing key, or a mentor that is not an object, is still a `server` failure. A mentor whose `name` is blank is shown the same way, as no mentor (Issue #537); a name that is not a string is still a `server` failure.
- **The quiz carries no answer key** (Issue #150). Correctness arrives one answered question at a time from `POST /me/quiz-attempts/{id}/answers`, and the score from `finish`. The sample quiz grades inside `SampleCourseLearningRepository` only; no model holds a key, and none should be proposed as a response field.
- Sample-only fields (`CourseExercise.assignmentFeedback`, `assignmentAttachment`, `simulatesWrites: true`) are empty or false on every backend lesson — the real flow reads `assignment.submission.feedback`, and `assignment.attachment` is listed with the lesson's Course materials (`CourseExercise.allMaterials`, Issue #194), never in `AssignmentTab`.

**Lesson access (Issue #410; product-confirmed).** One rule on every screen, `lessonOpens` (`course_learning/domain/lesson_access.dart`): a lesson opens only when the server leaves it **unlocked** and it is **completed or the server's continue lesson** (`continue.lesson_id`, "the first unlocked, uncompleted lesson"). Any other unfinished lesson waits its turn even once its class date has come; a lesson whose class date has not come never opens. The server's lock is confirmed in the backend source (`origin/main` `c6e6ce0`): `app/services/learning/path.py` `is_locked(session) = session is not None and session.session_date > today()`, on the module's **first** class session (a module with no session is never locked); a lesson's `locked` *is* its module's (`module_lessons`). The client never recomputes it. The backend has no per-lesson class date — `ClassSession` carries `topic_id` (the module), no lesson — so every lesson of a module unlocks on that module's first class date; the turn-taking above is the client's, stricter than the server.

- **Client: navigation prevention.** Every entry point to a lesson's content opens it only through `openLesson` (`course_learning/presentation/lesson_navigation.dart`), which asks `lessonOpens` with what the server said of the lesson; no other lesson is ever pushed, and the controls themselves are inert by the same rule: Junior Home's nodes (`JuniorMapNode.opens`), Course Detail's "Continue learning" (the continue lesson; inert when its module is locked) and the Lesson List's rows (given the course's continue lesson by Course Detail). Course Detail's module cards stay inert while `locked`. The quiz is reached only from inside an opened lesson. Adult Home, the cohort list, the course catalog's detail, the certificate screen and Junior Home's course card open Course Detail only — never a lesson directly; no named route or notification tap opens a lesson. Should a refusal reach the lesson screen anyway, `409 lesson_locked` reads as `CourseLearningFailureKind.locked` and shows the generic error, no content (no locked-lesson copy exists: `PRODUCT DECISION`).
- **Server: enforcement.** `ensure_module_open` answers `409 lesson_locked` on `GET /me/lessons/{id}`, `POST /me/lessons/{id}/complete`, `GET /me/materials/{id}/download`, `GET /me/assignments/{id}` and its `POST …/submissions`, and `POST /me/quizzes/{id}/attempts`. `GET /me/modules/{id}/lessons` lists a locked module's lessons by design — titles and flags, no content.
- **Evidence — out-of-order progress is in the data, not made by the app (Issue #410 device report).** The app never completes a lesson: `CourseExerciseDetailController.completeLesson` exists but no control calls it (Issue #209), and reading a lesson (`GET /me/lessons/{id}`, backend `lesson_detail`) only reads `LessonProgress`. Server-side, only `POST /me/lessons/{id}/complete` (`complete_lesson`) and the seed write it. The junior course `junior-ai-summer-10-14` is a seeded programme (`app/seeds_programmes`, `summer-kids`): one class per lesson from 2026-06-16, so every module's first class is past and nothing is locked, and `record_progress` skips lessons at random by each student's "diligence". Replayed offline, seeded student `jr10.s10` completes `·✓✓✓·✓✓·✓··` — 6 of 11, the 54% seen on the device — so the path shows padlocks between ticks: lessons 5, 8, 10 and 11 left unfinished while later ones were completed. That this is the device's account is inferred from the 54%, not verified against its response. `test/features/junior_home/junior_lesson_audit_test.dart` holds the fixture.
- **`BACKEND GAP` — lesson order is not enforced:** the server would serve any unlocked lesson, not only the continue one; binding the order needs the backend's `locked` to carry it (the contract lets the lock rule change without changing the field).
- **`BACKEND GAP` (not reachable from the app, which never opens a locked lesson):** `PUT /me/lessons/{id}/note` checks enrolment only (`lesson_for_student`), so a note can be written on a locked lesson; and `POST /me/quiz-attempts/{id}/answers`, `…/finish` and `GET /me/quiz-attempts/{id}` check only the attempt's owner, so an attempt started while the module was open can still be read and answered after it locks again. Smallest backend change: call `ensure_module_open` in `put_note` (as `_open_lesson` does) and in `_own_attempt`'s callers for answers and the open-attempt read (via `_quiz_topic_id`). Client-side gating is not security; these need the backend change.

The contract is the source of truth for the API. `docs/course_learning_frontend_backend_requirements_v1.md` holds the field-by-field analysis that preceded it — historical context where the two differ.

## 8. Rules for touching this layer

1. **Never invent an endpoint, field, status code or business rule.** If a task needs one that is not in §1 or §2, stop and report it as a `BACKEND GAP`.
2. **Never widen a model on speculation.** A field is modelled non-nullable only where a confirmed response showed a value; `HttpCourseRepository` fails loudly on a missing required field precisely so the gap surfaces as a parse error rather than a silent wrong value.
3. **Do not convert sample data into an API contract.** Sample fields describe what the UI needs, not what the backend sends.
4. **Keep failure families separate.** Do not merge the failure enums to "simplify"; the split is what keeps `switch` statements honest.
5. **A new authenticated endpoint** reads its token from an injected `AuthSessionStore`, defaults its `http.Client` to `AuthenticatedClient.instance` (so an expired token is renewed and the request retried), uses `getRaw`/`postWithoutBody` (which return all statuses), and maps a 401 that survives renewal to that feature's "session expired" case.
